# NVD feed access runs keyless with Hangfire retries as the only resilience

The importer reads NVD through two channels: full-year archive feeds (`https://nvd.nist.gov/feeds/json/cve/2.0/nvdcve-2.0-{year}.json.zip`) for the initial/daily catch-up, and the REST 2.0 API (`services.nvd.nist.gov/rest/json/cves/2.0`) for the hourly modified-since delta. Both are accessed **keyless** — there is deliberately no NVD API key in configuration — and clients come from `IHttpClientFactory` with the default 100 s timeout. Resilience is **not** implemented in the HTTP layer: no Polly policy, no special-casing of 403/429 responses, no request pacing. Instead each import step persists a step marker, and failures (timeout, throttle rejection, bulk-write aborts) simply propagate so Hangfire's `AutomaticRetryAttribute` re-runs the whole step with its escalating backoff.

The trade-off point: NVD rate-limits the REST API per rolling window and keyless access sits in the smallest tier, so long windows reliably fail once or twice before a retry lands inside the budget — observed live as `TaskCanceledExceptions` on the year feed and throttle-triggered delta re-runs. Building pacing/Polly handling was rejected for now because the retry-and-handler model already converges (the database catches up within the hour), the extra machinery would need an NVD key to pay off, and eliminating Hangfire's retry loop in favor of in-process resilience would leave the soft-failure path (step markers, retries) inconsistent with the rest of the importer.

When this stops holding: if NVD beats the retry window (e.g. totalResults over several pages), or an NVD key is provisioned (`appsettings` would need the key + header wiring, and retries/paging could then pace inside one job run), this ADR should be amended rather than the policy quietly added per-helper.
