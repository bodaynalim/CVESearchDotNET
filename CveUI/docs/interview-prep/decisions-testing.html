2 · Decisions & testing

The differentiator material: decision narratives from the ADRs, the single-seam testing approach, and the zoneless test discipline.

Theme: ADR culture as interview communication

What to say
"We record architectural decisions with the alternatives we rejected and why — so the answer to 'why did you do it this way' is already written down, not reconstructed."

ADR 0002 — the URL is the source of truth for all list state

The Vulnerabilities page serializes its full listing state as query params bound as component inputs; / redirects to /cves so the list is the app's default view. The rejected alternatives are recorded, and naming them is the interview skill:

  • Over a separate search route for Global CVE search — one screen, one request shape, one URL grammar to document (same page scoped v. unscoped).
  • Over in-page state — a shareable, bookmarkable Result set was a requirement for this tool.

The contract's consequences are precise: a new Keyword takes effect only on submit (Enter or Search) and resets page to 1; sort and page-size changes keep the page unless the Result set no longer covers it (clamped — see page 1). The Weaknesses page follows the same contract (q, page, count). Any new listing state must land in the URL first, with an input binding and a spec.

ADR 0001 — one HTTP-boundary test seam

All UI behavior tests run real components with real routing through the whole app shell, stubbing only HTTP. The rejected alternatives, verbatim rationale: "Isolated component tests and mock-service tests repeatedly drifted from real behavior — query-param binding, zoneless scheduling, resource error semantics." Runtime semantics live in the integration of router → component inputs → resource scheduling; behavior asserted is "does this route issue this request and render this table", never internals.

Likely probe

"Is that ADR culture or paperwork?" — It pays off immediately: when new teammates onboard or a reviewer asks "why," the rejected alternatives are the answer. The glossary complements it — terms like Keyword come with avoid lists, so UI copy, code names, and interview phrasing stay aligned.

Theme: The single-seam testing approach

What to say
"Test through the boundary, not at it. One seam: the network. We rejected mock-service tests because they encode implementation, not behavior — our tests survive refactorings that would shred them."

What the code does

src/app/testing/boot-app.ts boots the real shell with production DI providers wholesale, overriding exactly two things: API_BASE_URL and the testing HTTP backend (provideHttpClientTesting()). Interceptors, routing, and every component ship to prod unchanged.

  • Tests drive the app through real routing — navigating to a URL, flushing the resulting request, asserting rendered output.
  • The stubbed payloads are camelCase on purpose (see ADR 0001's cross-reference with the API-side ADR): the wire contract is a stack-wide agreement, and the test doubles encode it.
  • Per-test setup is heavier, failures are less pointable. Counter: assert-at-the-boundary tests don't break when internals are renamed, and the app has no more natural seams than the one that was rejected.

Tradeoff to concede willingly

"Yes, pure logic like the CVSS severity mapping gets its own unit specs despite the integration-first stance — where logic is pure, it's trivially worth a direct test. The seam decision governs behavior tests, not pure functions."

Theme: Zoneless change detection & the test discipline

What to say
"The app runs zoneless — no zone.js. That has a real testing consequence: whenStable() never resolves while an httpResource request is in flight, so our seam's contract is flush-then-await, in that order."

What the code does

  • app.config.ts: provideBrowserGlobalErrorListeners() + no zone-based scheduler; scheduler work (change detection, new-route resource request creation) lands in macrotasks.
  • boot-app.ts's settle(): one macrotask (setTimeout(resolve, 0)) so scheduler effects run before assertions.
  • Tests call fixture.autoDetectChanges() — nothing pumps change detection for them.
  • The documented ordering rule: pending API requests must be flushed before awaiting whenStable(); a hung test is the symptom of doing it backwards.

Quote this sequence in an interview; it demonstrates zoneless system understanding rather than component-level trivia — scheduling, macrotasks, resource lifecycles, and test ergonomics in one sentence.
