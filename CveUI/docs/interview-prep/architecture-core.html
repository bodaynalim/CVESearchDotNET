1 · Architecture core

State ownership, the reactive data layer, and the clamp effect — the three themes every later theme assumes.

Theme: Signals-first state ownership

What to say
"State is split by ownership: the URL for listing state, signals for derived and ephemeral state, localStorage for Recent lookups. There's no global store — the URL is the store for anything shareable, per ADR 0002."

What the code does

On the Vulnerabilities page, every listing param — vendor, product, q, page, count, sort, direction — is a plain input<string>() bound straight from the URL query params by withComponentInputBinding() (src/app/app.config.ts). The page holds none of it itself (ADR 0002: "in-page-only state is a violation of this record").

Derived state is pure computed() from those inputs: parse-and-guard functions (src/app/pages/cve-list.page.ts, parsePage/parsePageSize/parseSortField) coerce any malformed or out-of-set URL value back to a default, so a hand-edited URL like count=999 degrades to 25 instead of erroring — the API would 400 on values the page never sends.

Recent lookups is a signal seeded from localStorage (src/app/core/recent-lookups.ts): IDs are normalized, deduplicated, capped at the last five — and both read and write are wrapped in try/catch so disabled storage or privacy modes degrade silently to empty history. Failed lookups never reach it.

Likely probes

"Why no NgRx?" — The state topology is shallow: server data (owned by httpResource), URL state (owned by the router), browser-local state (one signal). A store would duplicate the URL, and ADR 0002 forbids exactly that: "any new listing state must land in the URL first".
"What's the risk of URL-as-state?" — Caps on param length (mitigated: every param is a short scalar), and the param grammar becomes a public contract (mitigated: strict typed parsers whitelist sort to 'published' | 'modified' and count to the page-size set).

Theme: The httpResource data layer

What to say
"Data fetching is httpResource with a computed request getter; returning undefined idles the resource — no request is ever issued for a state that doesn't need data. Exactly one listing request and one count request are ever live."

What the code does

src/app/core/api/http-resource.ts wraps httpResource() in runInInjectionContext: httpResource throws NG0203 outside an injection context, and this wrapper is what lets API-facade services — not just components — create resources.

src/app/core/api/cve.api.ts is a set of typed facades:

  • searchByProduct — vendor+product scope, path-segment encoded (vendor names and Keywords contain spaces and slashes).
  • list — a discriminated union { kind: 'all' } vs { kind: 'keyword'; keyword } decides between the global and keyword endpoints.
  • counts, detail, last-published / last-modified — each a resource with its own getter.

On the Vulnerabilities page two listing resources exist (productResults, unscopedResults), but the inactive one's getter returns undefined and its Filters do not change, so only the active mode ever generates a request. The same trick keeps the two count resources idle except for the active mode — and the count refetches only when the Result set changes, never on page turns.

Likely probes

"Resource vs Observable vs async pipe?" — Resources are stateful and signal-native: isLoading(), error(), value() map one-to-one onto the template's four-way render branch (loading / vendor-product-not-found / failed to load / list). No subscription management, no async pipe, no manual flag soup.
"Who validates page params?" — A documented split: the backend owns validation (a 400 on out-of-range values, per the comment in cve.api.ts), the page owns sending well-formed values (page-size whitelist, clamped page numbers).

Theme: The effect() + untracked() page clamp

What to say
"An effect clamps the URL page back into range when a re-sort or smaller page size shrinks the Result set below the current page. total is its only dependency; the page descriptors are read with untracked so changing those doesn't re-trigger the clip — they already refetch through the computed request params, and re-writing the URL from an effect that also reads it would ping-pong."

What the code does

// src/app/pages/cve-list.page.ts — the clamp effect
effect(() => {
  const total = this.total();          // dependency: the fetched count
  if (total === undefined) return;
  const count = untracked(this.pageSize);
  const page  = untracked(this.pageNumber);
  const last = lastPageOf(total, count);
  if (page > last) this.patchQueryParams({ page: last });
});

This is a reaction, not a derivation: an HTTP response changes a value that forces the router URL to change. Effects are the sanctioned tool for side-effect-on-change; untracked prevents dependency explosion. That vocabulary — tracked vs untracked reads, effects as the side-effect boundary — is exactly what signal-era interviewers probe.

Likely probe

"Why not a computed or a store?" — A computed can only produce a value, not write back to the URL; a store would duplicate state. The effect writes once, the new URL re-binds the inputs, and the cycle terminates — a deliberate single writer at the router boundary.

The keyword submit, in the same narrative

submitSearch() (Vulnerabilities page) lands the new Keyword in the URL via router.navigate([], { queryParams, queryParamsHandling: 'merge' }). Passing null for a query param removes it — the basis of "a new Keyword resets page to 1, but sort and page-size changes keep the page" from ADR 0002. Note the Keyword match semantics (case-insensitive substring) live API-side; the UI only owns the submit-to-URL flow.
