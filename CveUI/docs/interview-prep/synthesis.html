4 · Synthesis

Full-stack passing lanes, the three-minute opening narrative, and the rapid-fire defaults — then the guide is complete.

Theme: Full-stack camera passes

What to say
"The SPA is read-only and holds no server-side state; it treats URLs as the browsable source of truth. Where a full-stack interviewer pulls a thread across the stack, I can answer from the UI half without stretching out of scope."

Threads a full-stack interviewer pulls

  • camelCase wire contract — payloads are camelCase stack-wide; the UI treats it as the contract (ADR 0001's cross-reference with the API-side decision), no client-side snake_case adapters. If asked why: one naming convention from MongoDB backend to rendered Angular template.
  • Error semantics at the seam — the UI distinguishes 404 ("vendor/product pair not found") from other failures ("Failed to load CVEs"), shaped via the not-found interceptor wired in src/app/app.config.ts. Error classes are decided at the boundary, not guessed per template.
  • Keyword semantics live API-side — case-insensitive substring matching is defined in the .NET API; the interface only own the submitted-Keyword-to-URL flow. State it plainly: "matching is defined API-side; the page only carries the Keyword."
  • Read-only topology — the tool never writes to the server; pagination state per a Result set stays consistent because one count request serves every page turn of the same Result set, and list state lives in the URL.

Likely probe

"What happens on refresh mid-search?" — Nothing is lost: every listing param is in the URL, the inputs rebind, the resources refetch. That single answer demonstrates the whole state topology from page one.

The three-minute opening narrative

When asked "describe this system," walk the Vulnerabilities page end-to-end. Five beats:

  1. Topology — "Read-only Angular SPA over a CVE Search API. No server-side state. The URL is the source of truth for all list state — refresh, back/forward, deep links restore everything."
  2. Inputs — "Query params bind directly as component inputs via withComponentInputBinding — the page is a pure function of its URL."
  3. Guards — "Computed parse functions whitelist and clamp every value before it travels — a malformed URL degrades to defaults, and the API never sees an out-of-set count or sort."
  4. Data — "httpResource facades with getters that return undefined to idle: exactly one listing and one count request live at a time; the count serves all page turns of a Result set."
  5. Reactions — "One effect uses the fetched total to clip the URL page back into range, reading the page descriptors untracked to avoid a write-read cycle. Tests boot the real shell with only HTTP stubbed — one seam."

That answer touches signals, resources, routing, testing, and validation in three minutes — and every sentence has a page of backup in this guide.

Rapid-fire defaults

Short answers to the probes that come with no follow-up:

Zoneless?
Yes — no zone.js; scheduler work runs in macrotasks; tests call autoDetectChanges() and flush requests before whenStable().
RxJS or signals?
Signals inside components; RxJS only at event-stream boundaries, bridged with toSignal (shell title) and httpResource under the hood for data.
State store?
No global store. URL owns listing state (ADR 0002); signals own derived and browser-local state; localStorage is wrapped in try/catch on both read and write (privacy modes degrade to empty history).
Testing stack?
Vitest + jsdom, one HTTP-boundary seam via a bootApp() helper that ships production DI providers with only the backend swapped; stubbed payloads are camelCase to encode the wire contract.
Why current majors?
httpResource, built-in control flow signals, and zoneless are all recent — betting on Angular 22 / TS 6 / Tailwind 4 was deliberate, and the guide names that bet to show it was made knowingly.
